# C5 — Confidence band calibration

**Epic:** Eval Corpus & Harness

**Priority:** Critical

## User story

As the founder building Vitalog,
I want a calibration script that searches `THRESHOLD_AUTO_ACCEPT` × `THRESHOLD_REJECT` against the eval corpus, picks the best-precision/recall pair, and writes the constants into `src/ingestion/structurer.py`,
So that the three-band confidence model is grounded in measurement, not gut feel, before the demo runs.

## Why this matters

The three-band model is one of the headline safety mechanisms of the system, but the bands are nothing without calibrated boundaries. Architecture Appendix D mandates this calibration as a deliverable; project CLAUDE.md Gotchas hard-rules that thresholds never change without re-running this script.

## Acceptance criteria

1. **Given** the eval corpus + the extraction pipeline, **When** I run `make calibrate`, **Then** the script sweeps `THRESHOLD_AUTO_ACCEPT ∈ {90, 92, 95, 97, 99}` × `THRESHOLD_REJECT ∈ {60, 65, 70, 75, 80}` and produces a 5×5 grid of (precision, recall) pairs.
2. **Given** the grid, **When** the script picks the best pair, **Then** the rule is documented: maximize auto-accept-band precision subject to recall ≥ 0.95 in the auto-accept band AND review-band precision ≥ 0.80.
3. **Given** the chosen pair, **When** the script completes, **Then** `eval_corpus/calibration_report.md` exists with: the full grid, the chosen pair, the rule applied, and a per-band confusion matrix.
4. **Given** the chosen pair, **When** the script completes, **Then** `src/ingestion/structurer.py` has `THRESHOLD_AUTO_ACCEPT` and `THRESHOLD_REJECT` set to the chosen values via a generated constants block at the top of the file (marked with `# generated by calibrate; do not edit by hand`).
5. **Given** any subsequent run of the test suite, **When** the constants drift from the latest calibration report, **Then** a test in `tests/ingestion/test_threshold_constants.py` fails — enforcing the project CLAUDE.md rule.
6. **Given** the calibration report, **When** I read it, **Then** the chosen pair is reproducible: same corpus + same pipeline + same seed produces the same constants.

## Implementation notes

- The grid is intentionally coarse (5×5) because the corpus is small (~18 docs); finer granularity overfits.
- "Precision" in the auto-accept band = of records routed to auto-accept, what fraction had a correct ground-truth value? "Recall" = of all correct values, what fraction made it to auto-accept? Document these definitions in the report.
- If no grid cell meets the rule, the script emits the closest cell + a `CALIBRATION FAILED` banner in the report; capstone falls back to the initial constants (95, 70) and the founder must decide.
- The structurer constants block is written by string substitution between markers in the file; never use `exec()` to inject.
- Calibration must be re-run after any structurer prompt change. The drift detector test compares the constants currently in code to the chosen values in the latest report.
- Cost: one full calibration run costs roughly the same as one C3 run (~$1–2 in tokens). Budget for 2–3 runs in capstone.

## Verification

- `make calibrate` — completes, produces the report, updates the constants
- `pytest tests/ingestion/test_threshold_constants.py -q` — drift detector passes after calibration
- Manual: open `calibration_report.md`, sanity-check the grid + chosen pair
- Reproducibility: `make calibrate && cp eval_corpus/calibration_report.md /tmp/r1 && make calibrate && diff /tmp/r1 eval_corpus/calibration_report.md` — only timestamp differs
